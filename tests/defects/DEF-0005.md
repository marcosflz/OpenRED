# DEF-0005 — Deadlock de imports concurrentes de `scipy` entre hilos del RPC

| Campo | Valor |
|---|---|
| **ID** | DEF-0005 |
| **Severidad** | alto (el motor se queda colgado y deja de responder a cualquier petición) |
| **Estado** | corregido (A1/A11) |
| **Componente** | engine `openred_engine/rpc.py`, `plugins/loader.py`, `warmup.py` |
| **Detectado en** | `c2250d0` · `A11` (integración) · 2026-09-25 |
| **Corregido en** | A11: warm-up single-thread + `_LOAD_LOCK` en el cargador de plugins + lock de resolución de servicios |
| **Matriz §4.2** | `T1-1`, `T2-3`, `T2-6` (descubrimiento de plugins en paralelo) |
| **Fixture / prueba** | `engine/tests/test_rpc_integration.py` (ping + plugins + cálculo concurrente) |

## Resumen

El servidor RPC atiende cada petición en su propio hilo. Si dos peticiones que provocan el
**primer** import de un submódulo de `scipy` (`scipy.interpolate`, `scipy.optimize`) coinciden en
el tiempo — por ejemplo dos `plugins.list` (GrainLibrary y NozzleLibrary) seguidos — el
cargador perezoso de scipy se bloquea mutuamente y el proceso deja de responder para siempre
(ni siquiera a `app.ping`).

## Reproducción

```bash
# Cliente mínimo: dos peticiones seguidas sin esperar a la respuesta de la primera
python - <<'PY'
# abre el sidecar y envía:
#   {"id":1,"method":"plugins.list","params":{"library":"GrainLibrary"}}
#   {"id":2,"method":"plugins.list","params":{"library":"NozzleLibrary"}}
PY
```

Resultado observado (antes de la corrección):

```
STDOUT: {"id": 1, "result": {... Tubular-Grain ...}}
WATCHDOG: killing engine
STDERR:   File ".../scipy/interpolate/_interpolate.py", line 12 in <module>
          ... _handle_fromlist ...  (hilo 2, bloqueado dentro del import de scipy)
```

Resultado esperado: ambas respuestas en milisegundos (o, como mucho, el coste normal de importar
matplotlib/scipy una vez).

## Causa raíz

- `openred_engine/rpc.py` lanza un hilo por petición (necesario para `request.cancel` y streaming).
- `openred_engine/plugins/loader.py` (`load_library`) y los proxies `services/__init__.py` hacían
  los imports en esos hilos sin serializar.
- El cargador perezoso de `scipy` (`scipy/__init__.py`) no es thread-safe: dos primeros imports de
  submódulos distintos desde hilos distintos pueden quedar en espera cruzada.

## Impacto

- Un usuario que abriese la pestaña de motor y la de tobera a la vez podía colgar el sidecar.
- El síntoma es especialmente confuso porque el proceso sigue vivo (el supervisor de Rust no lo
  reinicia: solo detecta la muerte del proceso, no el cuelgue).

## Corrección

1. `openred_engine/warmup.py`: importar `numpy`, `scipy.optimize`, `scipy.interpolate`,
   `matplotlib` (+ `pyplot`, `patches`, `cm`) y `pyserial` **antes** de aceptar peticiones, en el
   hilo principal (`__main__.py` llama a `warm_up()` antes de `serve_forever`).
2. `plugins/loader.py`: `_LOAD_LOCK = threading.RLock()` alrededor del escaneo/import de plugins.
3. `services/__init__.py`: `_RESOLVE_LOCK` alrededor de la resolución perezosa de servicios.
4. `apps/desktop/src-tauri/src/sidecar.rs`: `READY_TIMEOUT` sube a 30 s (el warm-up retrasa el
   evento `ready` en instalaciones con la caché de matplotlib vacía).
